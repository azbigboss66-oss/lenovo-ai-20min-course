# 详细讲稿：从一句话到一种能力

> 讲师说明：方括号内容为动作或屏幕提示，不需要念出。来源编号对应 `research/sources.md`。全部业务材料均为教学模拟，不代表联想真实项目或内部制度。

## 0:00–2:00｜先从大家每天都会遇到的一句话开始

[屏幕显示：把下面会议内容整理一下。]

各位同事好。今天只有二十分钟，我不准备带大家巡览几十个 AI 名词，也不要求大家写代码。我们只解决一个问题：怎样把 AI 从“偶尔聊两句的工具”，变成真正能进入工作流程、而且结果可检查的能力。

先看屏幕上这句话：“把下面会议内容整理一下。”这句话很像我们工作中随手发给同事的消息。人与人合作时，对方了解项目、认识参会者，也许知道管理层关心什么，所以能补全很多没有说出的背景。但模型并不天然拥有这些共同背景。

[显示一段模拟会议记录：项目代号 Horizon；试点材料需在周四前完成；王宁负责样机清单；培训日期尚未确认；客户名称用“客户 A”代替。]

如果只说“整理一下”，模型可能写成长摘要，也可能列行动项，还可能为了让文本完整，把“培训日期尚未确认”改成一个看起来合理的日期。文字可能很顺，但我们真正需要的是给谁看的、什么格式、哪些事实不能猜、怎样才算完成。

[切换前后对比。]

第二个请求明确告诉模型：为项目负责人生成一页周报；只使用原始记录；分为本周结论、风险、行动项和待确认事项；行动项必须含负责人、截止时间与依据；没有提供的信息写“未提供”；不得补充客户身份；最后做一次字段自检。这时结果更容易使用，也更容易验收。

大家先记住第一个结论：AI 的问题经常不是“它够不够聪明”，而是我们有没有把工作说成一个可执行、可验收的任务。

## 2:00–5:30｜模型为什么能写，也为什么会编

[屏幕显示：输入 → 推断 → 输出 → 影响。]

我们先给 AI 一个准确但不复杂的定义。OECD 的表述是：AI 系统从收到的输入中，推断如何生成预测、内容、建议或决策等输出，这些输出会影响物理或虚拟环境。[2] 这句话里最重要的不是“像不像人”，而是四个词：输入、推断、输出、影响。

生成式 AI 是其中擅长生成内容的一类。今天我们使用的大语言模型，会先把文字拆成 token。token 可以是一个字、词的一部分、标点或其他文本片段。模型根据当前上下文，计算接下来哪些 token 更可能出现，然后一个接一个地产生结果。[3]

大家可以把它想成一位读过大量材料、非常会续写的同事。这个类比只帮助入门。技术上，模型不是在资料库里逐句复制答案，而是通过参数中学到的模式进行概率生成。Transformer 的自注意力机制会衡量上下文中不同 token 之间的联系，所以它能处理长句、归纳结构和保持语气。[4]

这里有一个重要推论：高概率不等于事实。假设会议记录写着“培训日期待确认”，模型知道项目周报中经常出现日期，于是可能生成一个形式正确但来源不存在的日期。这不是模型在故意说谎，而是生成机制在补全一个看起来合理的序列。

NIST 把这种自信地产生错误或虚假内容称为 confabulation，中文常说“幻觉”。[5] 所以，流畅度只能证明模型会表达，不能证明信息真实。以后看到一段很漂亮的 AI 输出，我们要多问一句：哪一部分来自原始材料，哪一部分是模型推断，哪一部分需要人确认？

[屏幕显示：输入检查、输出检查。]

在企业环境里，还要做两次检查。输入前检查：这些信息能不能交给当前获准的工具，是否包含客户、员工、序列号、价格、未公开计划等敏感内容。输出后检查：关键事实有没有来源，结论由谁负责，错误能不能被发现。今天所有案例都只使用模拟材料；真实工作必须遵循公司当时有效的工具、数据和审批要求。

## 5:30–10:30｜Prompt：把愿望翻译成任务合同

[屏幕显示：Prompt 不是咒语，是本次工作的任务合同。]

现在回到最开始的请求。Prompt 最朴素的含义，就是我们给模型的输入和指令。网上常见的技巧是先写“你是一位世界顶级专家”。角色可以帮助统一语气和观察角度，但它不会凭空给模型增加项目事实，也不能代替权限、数据或验收标准。

有效 Prompt 的共同点，是把模型完成任务所需的条件说清楚。官方提示工程资料通常强调明确指令、相关上下文、输出要求和示例；给少量输入输出范例叫 Few-shot，它是在本次上下文里展示模式，不是训练模型。[6]

例如，若我们要求模型把问题分成“进度、风险、决策、待确认”四类，与其再写一段抽象解释，不如各给一个简短的输入输出示例。但示例不是越多越好：样例必须具有代表性，不能把错误标签或敏感信息复制进去；任务规则变化后，也要同步更新示例。

为了便于工作中记忆，我把它整理为五个字段。请注意，这是本课程的记忆框架，不是唯一行业标准。

[依次显示五个字段。]

第一，目标。说明最终要完成什么、给谁使用。不是“整理一下”，而是“为项目负责人生成一页周报，使其能判断进展、风险和下一步”。目标决定模型应该筛选什么。

第二，必要上下文。把原始会议记录、名词解释、时间范围和允许使用的资料交给模型。上下文不是越多越好，而是与任务相关、来源清楚。若需要当前内部制度或最新产品参数，应从获准的知识源检索，而不是要求模型凭记忆回答。

第三，约束条件。比如只依据提供材料，不补充客户身份；保留代号；不把推测写成事实；中文控制在六百字以内。约束是在提前处理已知失败模式。

第四，输出形式。说明需要几个部分、什么顺序、表格包含哪些列。模型能够自由写作，但工作交付往往需要固定接口。我们要求行动项表包含“事项、负责人、截止日期、依据、状态”，后续检查和协作就容易得多。

第五，验收与停止。告诉模型怎样算完成，也告诉它证据不足时怎么办。例如，负责人或日期缺失时写“未提供”，把冲突信息放入“待确认事项”；如果原始材料为空，停止生成并请用户补充。这个字段把“不要瞎编”变成可观察的行为。

[屏幕展示完整 Prompt。]

现在完整版本是：

“请根据下方会议记录，为项目负责人生成一页中文周报，帮助其判断本周进展、主要风险和下一步。只使用记录中的事实，不调用外部知识，不补充客户真实身份。输出依次包含：三条以内本次结论；风险与影响；行动项表；待确认事项。行动项表必须包含事项、负责人、截止日期、原文依据和状态。负责人、截止日期或状态缺失时写‘未提供’，禁止推测；没有被明确提出的行动不得自行新增。全文不超过六百字。提交前检查每项行动是否能在原文找到依据；如原文为空则停止并要求补充。”

请大家用十秒钟想一下：这段 Prompt 中，哪一条最能降低“看起来完整、实际上编了事实”的风险？

[停顿。]

答案可以有两个：一是“只使用记录中的事实”，二是缺失时明确写“未提供”。再加上原文依据列，我们不只让模型少猜，还让使用者能够检查。

Prompt 不是越长越专业。一个好的 Prompt 只保留影响结果的目标、材料、边界、接口和验收。任务简单时可以很短；风险和协作成本高时，才需要更明确的合同。

## 10:30–15:30｜Skill：把一次成功变成可复用流程

[屏幕显示：Prompt 解决这一次，Skill 解决这一类。]

如果这项工作每周都要做，我们会遇到新问题：每个人保存的 Prompt 不同；输出格式慢慢漂移；公司模板更新后旧 Prompt 没人维护；负责人缺失时有人让模型猜，有人留空。此时需要管理的已经不是一句话，而是一种重复性能力。

开放 Agent Skills 规范把 Skill 组织成一个目录。入口是 `SKILL.md`，还可以有脚本、参考资料和输出资产。系统先看到 Skill 的名称和触发描述；确认任务匹配后再读取完整说明；需要时才加载资源。这叫渐进式披露，可以避免每次把全部资料塞进上下文。[7][8]

[展示目录。]

我们的教学示例叫 `meeting-to-action-skill`。目录里不仅有 `SKILL.md`、输出合同和检查脚本，还配有正常、缺字段、冲突和授权不明四类输入与标准答案。课堂使用同一份 Horizon 记录，从 Prompt 初版走到标准答案，再运行检查，形成可复现闭环。

为什么要有脚本？因为模型擅长理解和生成语言，但“表格是否正好五列、每行列数是否一致、缺失字段是否写成规定值”是确定性问题，交给程序检查更可靠。模型负责语义工作，脚本负责机械规则，人负责业务真实性和最终决策。

一个能进入实际工作的 Skill，至少回答八个问题：什么时候触发；什么输入是必需的；步骤是什么；允许读哪些资料；哪些检查交给工具；遇到异常怎么办；什么时候必须停下来问人；最终输出遵守什么合同。

系统化制作 Skill 可以分成五步。

第一步，选任务。优先选择高频、边界清晰、成功标准能够说明的工作，例如会议记录转行动项，而不是“替我管理整个项目”。

第二步，观察真实执行。记录一次高质量完成过程和人工修改，找出稳定步骤、容易遗漏的字段和真正需要判断的地方。注意，正式项目要使用经过授权和脱敏的样例；本课只用模拟数据。

第三步，拆分资产。把共同规则放在 `SKILL.md`；较长的字段定义或制度说明放进 `references`；反复进行的确定性检查放进 `scripts`；输出模板放进 `assets`。不要把所有资料堆进一个超长文件。

第四步，写异常和停止条件。输入为空就停止；负责人未知就写“未提供”；事实冲突进入待确认；涉及未授权系统动作就停在建议阶段。可靠流程的专业性，很大一部分来自知道何时不能继续。

第五步，评测和版本化。准备几个真实感任务，其中至少一个边界样例；分别比较有 Skill 和没有 Skill，或者新旧版本的结果；用明确断言检查结构，用人工复核判断是否真正有用，并记录模型、Skill 版本、时间与成本。[10] 本仓库的本地模型运行记录只是一次教学快照，不代表换模型、换输入后仍然得到相同结果。

[屏幕显示：同一模型、同一输入——模糊基线 1/4，Skill 4/4；n=4，教学模拟。]

我们用同一模型、同一输入跑了对照：基线 1/4，Skill 4/4，基线还虚构了日期和行动。但样本只有四个，授权案例由运行器在模型前拦截；它只说明合同改善了可检查性，不是准确率声明。

这里必须澄清：看到一个 `SKILL.md`，不等于它已经在生产系统中自动运行。真正的 Skill 系统还需要兼容的 Agent 环境、技能选择、资源加载、权限控制、执行记录和评测。我们展示的是候选过程包和验证方法，不是生产部署证明。

还要把 Skill 当作过程资产，记录版本、负责人、适用范围、输入输出合同和评测结果。规则改变时用同一组任务比较版本。这样出问题后，我们能回答“用了哪一版、基于什么资料、哪里检查过”。

## 15:30–18:30｜专业判断：先定位问题，再选择技术

[屏幕显示七行诊断表。]

现在把视角再抬高一层。很多 AI 项目一遇到效果问题就说“是不是要微调”，这相当于发现周报格式不统一，就先考虑重新培养一个团队。专业做法是先定位失败发生在哪一层。

如果只是这一次目标没说清，改 Prompt。如果模型缺少最新、内部或指定来源事实，用受控检索，也就是常说的 RAG，把相关资料在请求时提供给模型。[13] 如果任务必须查系统状态、计算数据或提交操作，需要的是获准工具。工具给模型“手”，Prompt 只给它“话”。

这套判断可以用一句话记住：先修任务，再补知识，再接工具，再固化流程，最后才考虑改参数。每增加一层能力，也增加一层权限、成本和验证责任，所以技术选择不是追求最复杂，而是在约束下选择足以完成任务、且能够证明有效的最小方案。

如果同一流程反复执行，用 Skill 或固定工作流固化步骤和输出。如果步骤无法预先写死，需要模型根据环境反馈动态选择工具，才进入 Agent。研究和工程经验都提醒我们，Agent 的灵活性同时带来延迟、成本和误差累积，因此应从最简单的有效方案开始。[11][12]

只有当目标、知识和工具都已经合理，在一组代表性样例上仍出现稳定、重复的行为缺口，才评估微调。监督微调是用任务输入和理想输出示例改变模型的行为倾向。LoRA 则冻结基础模型的大部分权重，用较小的低秩矩阵学习更新，以降低可训练参数和内存需求。[15]–[17]

微调不是给模型安装一个随时更新的知识库，也不自动消除幻觉。它需要高质量代表性数据、独立验证、成本比较、隐私审查和回归检查。预训练更靠下层，解决广泛能力形成，涉及海量数据、模型规模和计算预算的联合设计。[18] 这不是二十分钟课堂要操作的内容，但我们要知道它在地图上的位置。

请判断一个新场景：每周都要把会议记录整理成统一格式；缺负责人或日期时不得猜；以后还可能从内部项目系统读取最新状态。优先选什么？

[停顿。]

先把输出合同和缺失值规则写清，封装为 Skill 或固定工作流；如果确实要读取系统状态，再接入经过授权的检索或工具。微调不是第一步。所有升级之前，先用代表性样例定义成功和失败。评测不是最后考试，而是选择技术的导航仪。[14]

## 18:30–20:00｜把能力与责任一起带回工作

[屏幕显示：可交、可证、可责、可追。]

最后回到联想的工作环境。联想公开的负责任 AI 框架包含六个支柱：多样性与包容、隐私与安全、问责与可靠、可解释、透明，以及环境与社会影响。[19] 对我们今天的任务，可以转成四个更容易带走的问题。

第一，可交：这些输入是否允许交给当前工具。第二，可证：输出中的关键事实能否找到来源。第三，可责：谁负责复核和最终决定。第四，可追：是否保留使用的资料、规则、版本和检查结果。

现在再看开场那句话：“把下面会议内容整理一下。”二十分钟前，它只是一个模糊愿望。补上目标、上下文、约束、输出和验收，它成为一个可用 Prompt；把稳定步骤、资料、脚本、异常和停止条件封装起来，它成为候选 Skill；用代表性任务比较结果，我们才知道是否真的改善；只有评测证明当前层解决不了问题，才继续增加检索、工具、Agent 或参数训练。

今天请大家带走一句话：先定义结果，再提供证据；高频任务封装为 Skill；任何升级都由评测证明。AI 专业能力，不是知道最多术语，而是能把人的意图翻译成清晰任务、可复用流程和可验证结果。谢谢大家。
