# 第 06 课详细讲稿｜评测与模型升级路线：先证据，后技术

> 建议 28 分钟；其中数据演示、决策练习和讨论约 7 分钟。

## 0:00–3:00｜“感觉更好”不是发布证据

团队把 Prompt 改长了、换了更大的模型、加了 Agent，演示现场看起来很顺，于是说“效果明显提升”。这个结论缺什么？缺相同任务、相同评分和相同条件下的比较。

我把评测看成技术讨论的入场券，而不是项目结束时补的一张成绩单。只要失败还不能稳定复现，“换大模型”“做微调”就不是路线，而是技术焦虑。

生成式 AI 有随机性，好的演示也容易挑中成功案例。如果每次测试都换问题、换资料、换判断标准，我们永远不知道改动是否真的改善。今天的主题不是追求一个万能分数，而是学会用证据决定下一步技术。

本课会用仓库里的会议行动项 Skill 做一个小样本示范，再把视角上升到 Prompt、RAG、Agent、微调和预训练的选择。请始终记住：四个虚构案例只能教学，不能证明生产效果。

## 3:00–7:00｜最小评测的五个部件

第一，任务集。它要代表实际分布，包括正常、缺失、冲突和风险边界，而不是只挑最容易成功的例子。任务集要冻结版本，测试过程中不能看见失败后偷偷改题。

第二，基线。可以是原流程、无 Skill Prompt、旧模型或人工处理。没有基线，只知道候选得了多少分，不知道是否值得改变。

第三，评分规则。确定性字段可用脚本检查；语义质量、业务价值和语气通常需要人工 rubric。评分项必须在看结果之前定义。

第四，版本和 Trace。记录模型、Prompt、Skill、知识库、工具、时间、输入和输出。否则同一个“系统名称”下的结果不可复现。

第五，成本、时延和风险。准确率提高一点，但成本十倍、等待三分钟、风险扩大，未必是好方案。企业选择应看质量—成本—时延—风险的组合。

这里还要加一条：评测本身也会错。自动评分器可能偏爱某种措辞，人工评分会不一致。高影响任务要抽样复核评分，并记录无法自动判断的项目。

## 7:00–11:00｜课堂证据：为什么 1/4 到 4/4 仍然要克制

仓库保存了同一本地模型在四个案例上的两组输出。模糊基线通过 1/4；加载会议行动项 Skill 后通过 4/4。检查内容包括字段完整、未知值保留、冲突暴露和未授权请求在模型前停止。

这个结果支持一个局部结论：在这四个已知虚构输入和当前评分合同下，候选 Skill 比模糊基线更符合预期。它还让我们看到改进来自哪里：不是模型参数变了，而是输入合同、步骤、停止规则和确定性检查变了。

为什么不能说“准确率从 25% 提升到 100%”？第一，四个案例样本太小；第二，它们由课程作者设计，可能与真实分布不同；第三，通过规则不等于业务内容优秀；第四，授权案例在模型前停止，与普通生成案例不是同一难度；第五，模型、硬件和提示版本会影响结果。

专业汇报要同时说结果和证据边界。克制不会削弱专业性，反而让决策更可信。

## 11:00–16:00｜先诊断失败，再选择技术层

如果输出没有理解任务目标、格式或未知处理，优先修改 Prompt。这是最便宜、最透明的一层。

如果缺的是最新、内部或指定来源事实，用受控检索或 RAG。不要用微调安装每天变化的知识。

如果任务必须读取系统、计算或执行动作，连接最小权限工具。工具解决外部状态，不解决模型是否会正确判断。

如果同类任务反复按稳定过程完成，用 Skill 或固定工作流固化资源、步骤、停止和检查。

如果路径确实不可预知，需要根据环境反馈动态选择工具，而且评测证明净收益，再考虑 Agent。Agent 不是对“流程复杂”的自动回答。

如果在大量代表性数据上，Prompt、上下文和流程都已稳定，但模型仍有一致的行为缺口，例如固定风格、分类边界或领域表达，再评估微调。

如果目标是形成广泛基础能力、新语言能力或从大规模语料建立模型，才进入预训练。这通常是大规模数据、算力和研究工程，不是普通应用项目的第一选择。

## 16:00–20:00｜微调、LoRA 和预训练到底改变什么

监督微调使用输入和理想输出样例继续训练模型，让其行为更贴近目标。它适合稳定、可重复、能收集高质量示例的行为问题。微调后仍会出错，也会产生回归，因此必须保留独立评测集。

LoRA 是一种参数高效微调方法。它冻结基础权重，学习较小的低秩更新，从而减少可训练参数和显存需求。白话说，它降低了适配成本，但没有免除数据授权、标注质量、偏差、版本管理和上线评测。

预训练是更基础的阶段。模型从大规模数据中形成广泛能力，需要设计数据、模型规模、训练 token 和计算预算。Chinchilla 研究提醒我们模型规模和训练数据要联合考虑。企业应用出现几个格式错误时直接谈预训练，通常是在错误层级解决问题。

一个实用判断是：需要“知道最新事实”，优先 RAG；需要“稳定怎样回答”，可能考虑微调；需要“访问或改变外部世界”，使用工具；需要“形成广泛基础能力”，才是预训练。

## 20:00–24:30｜练习：四个失败，应升级哪一层

请打开练习。四个模拟失败分别选择优先手段，并写一个必须先收集的证据。四分钟。

（两分钟独立完成；一分钟小组比较；一分钟追问选择微调或 Agent 的同学：为什么 Prompt、RAG 或固定工作流不够？）

讲评重点是“失败原因与技术作用匹配”。输出漏掉固定字段，先改 Prompt/合同并做结构检查；回答用了旧政策，用 RAG 和版本过滤；需要查询工单状态，接只读工具；在一千个代表性样例上仍稳定误分且输入信息完整，才可能进入微调评估。

即使答案是微调，下一步也不是立即训练。要先检查数据是否有权使用、标签是否一致、是否有独立测试集、上线后的成本和回退方案。

## 24:30–28:00｜把技术路线写成可审计决策

一份专业技术建议至少包含：观察到的失败、证据规模、当前基线、候选改动、预期影响、验证方法、风险和停止条件。不要只写“建议引入大模型微调以提升准确率”。

请把决策框架记成七层：Prompt、RAG、工具、Skill/工作流、Agent、微调、预训练。它不是每层都要走，而是提醒我们不要跳过更简单的解释。每次只改变主要一层，在同一评测集上比较，才能知道收益来自哪里。

下一课会把这些方法组合成联想场景综合实战，并用四个问题做最终审计：可不可以交、结果可不可以证明、责任由谁承担、过程能不能追踪。

今天带回岗位的动作：选一个你认为“模型不够好”的案例，先写下失败类型和三条代表性输入。只有当失败能够被复现，技术讨论才真正开始。

快速收束句：评测不是最后打分，而是技术选择的起点；最专业的升级，有时是决定不升级模型。
