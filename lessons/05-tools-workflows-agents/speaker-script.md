# 第 05 课详细讲稿｜工具、工作流与 Agent：自主性必须有边界

> 建议 25 分钟；其中架构判断练习与讨论约 6 分钟。

## 0:00–2:30｜文字里说“已完成”，不代表系统里真的发生

前四课都主要处理信息。现在加入动作。教学模拟中，一张服务工单要求：“查看最近日志，判断可能原因，更新工单状态，并向渠道伙伴发送通知。”如果只让语言模型回答，它可能写：“已完成更新并通知相关方。”但文字中的“已完成”不等于系统执行成功。

真正的外部动作需要工具：日志查询接口、工单 API、消息或邮件系统。工具一旦连接，AI 的错误就可能从一段错误文字变成真实状态变化。所以本课不是教大家追求最高自主性，而是学会把自主性和权限、风险、证据放在一起设计。

## 2:30–6:00｜四个层次：模型、工具、工作流、Agent

第一层是模型生成。输入文字，输出摘要、分类或草稿；它本身没有访问系统的能力。

第二层是工具调用。系统给模型一组明确函数，例如“读取工单”“查询只读日志”“保存草稿”。模型可以选择参数，真正执行由工具层完成。工具必须验证身份、权限和参数，不能相信模型说“我有权限”。

第三层是固定工作流。步骤由代码或规则预先定义：读取工单 → 查询指定时间范围日志 → 生成原因候选 → 人工选择 → 保存内部草稿。路径清楚、异常可枚举时，固定工作流往往更稳、更便宜、更容易审计。

第四层是 Agent。它根据目标和环境反馈动态决定下一步：可能先查工单，再根据错误码选择日志工具，然后补查知识库。ReAct 研究展示了推理与行动交错的基本模式。Agent 更灵活，但每一步都可能选错工具、传错参数或放大前一步误差。

“能动态规划”不是自动升级。只有任务路径确实不可预先列出，而且动态选择带来的收益在评测中超过成本与风险，才值得使用 Agent。

## 6:00–10:00｜动作风险不是一个“是否敏感”的开关

我们把动作分四级。

一级，只读：读取获准的工单、知识库或指标。风险仍包括越权读取、范围过大和敏感内容进入日志，但通常不改变外部状态。

二级，内部写入：保存草稿、添加内部标签、更新非关键字段。需要明确账户、允许字段、版本冲突和撤销方式。

三级，对外动作：给客户或伙伴发送消息、发布内容、创建会议。它会代表组织表达，必须预览收件人、正文和附件，并在发送前由有权人员确认。

四级，不可逆或高影响动作：删除数据、改变权限、批准付款、正式承诺价格或交期。这类动作通常不应由初级 Agent 自动完成，需要更严格的授权或完全排除。

风险分级要看情境。读取普通公开文档和读取含客户数据的工单都叫“读取”，控制要求却不同。一个按钮是否可撤销、影响范围多大、错误是否容易发现，都会改变设计。

## 10:00–14:00｜最小控制面：把“请谨慎”变成系统规则

第一，允许工具清单。只暴露完成任务所需的工具，不让 Agent 自由访问所有系统。

第二，最小权限。读取就不给写入；只能建草稿就不给发送；只能改当前工单就不给批量修改。

第三，参数校验。工单编号、时间范围、收件人和状态值都由程序校验；不要让模型生成任意查询或任意地址。

第四，预算、超时和无进展停止。Agent 不应无限循环尝试。预算不只是 token，也包括工具次数、耗时、影响范围和连续失败。

第五，人工确认。确认点必须展示将发生什么、作用于谁、使用什么参数，以及是否可撤销。一个只写“是否继续”的弹窗价值有限。

第六，Trace 与回滚。记录输入版本、工具调用、参数摘要、结果、人工决定和停止原因。可撤销动作定义回滚；不能可靠回滚的动作提高审批等级。

多步系统还要防止错误累积。假设每一步有九成把握，连续多步并不会自动保持九成；前一步拿错工单，后面再好的摘要也建立在错误对象上。因此每次工具调用后都要验证机器可检查的结果：返回对象是否匹配工单号、时间范围是否正确、状态码是否成功、结果是否为空。高风险链路在影响扩大前设置检查点，不要等到最后一封邮件生成完才发现第一步读错了数据。

工具失败也不能由语言模型用文字“修复”。超时、权限不足、参数非法和空结果应由运行层返回明确状态；模型只能解释或提出下一步，不能把失败包装成成功。连续失败达到阈值时停止，保留已经完成的只读证据并交给人。

## 14:00–17:30｜完整示范：服务问题分析停在发送之前

回到模拟工单。更合适的流程是：

一，用户选择工单，系统验证他是否有读取权限。二，只读取该工单关联时间窗口的脱敏日志。三，模型列出三个原因候选，每个候选附日志证据和不确定性。四，规则检查没有把猜测写成根因。五，生成内部处理建议和对外通知草稿。六，在屏幕上预览工单号、目标状态、收件人、正文和引用。七，由负责人确认后，外部系统才执行更新或发送。

在这里，Agent 可以帮助动态选择查询，但它不能自行宣布根因，也不能跳过确认。若日志为空、工具报错、需要超出当前工单的数据、收件人不在允许范围，系统停止并转人。

如果流程每次都完全相同，固定工作流比 Agent 更合适。只有错误类型很多、调查路径确实变化，才考虑在“只读分析”范围内引入 Agent，然后把写入和发送仍放到确定性审批之后。

还可以设置“权限递增”策略：候选阶段只生成；验证阶段开放限定只读；受控试点允许保存草稿；只有独立评测、审计和责任确认都满足后，才讨论更高影响动作。这样每次扩权都有证据门槛，也有可退回的上一级，而不是从聊天演示直接跳到自动执行。

## 17:30–22:00｜练习：为四个场景选择架构和确认点

请打开练习。每个场景选择“模型生成、只读工具、固定工作流或 Agent”，并标出人工确认点。四分钟完成。

（两分钟个人判断；一分钟小组比较差异；一分钟讲师随机追问：为什么不用更高级的方案？）

讲评的关键是“最小充分方案”。公开资料改写只需要模型生成。固定字段的每周报告适合工作流加 Skill。未知故障的只读调查可能需要受限 Agent。对外发送不因前面使用了 Agent 就自动放行，仍要人工确认。

如果答案是 Agent，还必须写清允许工具、最大步骤和停止条件；只写“因为任务复杂”不够。复杂任务也可能通过拆分为多个固定步骤解决。

## 22:00–25:00｜收束：专业不是放大自主性，而是匹配自主性

请记住四个层次和四级动作风险。工具解决“模型如何接触外部状态”；工作流解决“路径如何稳定”；Agent 解决“路径需要动态选择”；人工审批解决“责任不能交给模型”。

下一课会回答一个更难的问题：怎样证明 Agent、Skill 或微调真的比简单方案更好？我们会建立任务集、基线、评分和技术选择矩阵。

今天带回岗位的动作：画出你正在考虑自动化的一条流程，给每一步标 R、W、E、I——Read 只读、Write 写入、External 对外、Irreversible 不可逆。然后把确认点放在影响扩大之前，而不是流程结束之后。

快速收束句：Agent 的专业性不取决于它能做多少，而取决于它知道能做什么、何时停、由谁确认。
