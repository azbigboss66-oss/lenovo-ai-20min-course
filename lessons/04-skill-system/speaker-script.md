# 第 04 课详细讲稿｜Skill：把一次好结果变成工作能力

> 建议 27 分钟；其中仓库演示、练习和讲评约 7 分钟。

## 0:00–2:30｜收藏了一个好 Prompt，为什么换个人又做不好

很多团队的 AI 使用停在一个阶段：某位同事调出一条很好用的 Prompt，发到群里，大家收藏。两周后有人找不到模板，有人删掉关键约束，有人换了输入格式，结果再次漂移。问题不是 Prompt 没价值，而是一次委托还没有变成过程资产。

我的判断是：可复用的不是那段看起来聪明的文字，而是一套遇到缺失、冲突和未授权动作时仍知道怎样停下来的过程。没有停止和评测的 Skill，只是包装得更完整的愿望。

今天我们讲 Skill。课程中的定义是：可版本化、可复用的任务过程包。它把何时触发、需要的资料、执行步骤、确定性工具、异常停止、输出合同和评测放在一起。

这里先划清边界。一个目录里写了 `SKILL.md`，不代表系统已经会自动选择它、拥有业务权限、可以调用所有工具或已经通过生产验收。真正的业务能力还需要运行环境、选择机制、权限控制、版本记录、Trace、监控和人工责任。

## 2:30–6:00｜Prompt、工作流、Skill 各解决什么

Prompt 是本次请求的任务合同。它最接近一次工作委托，适合临时或变化较大的任务。

固定工作流把步骤和分支写进代码或流程配置，执行路径可预测，适合稳定、规则清楚的操作。

Skill 位于两者之间又连接两者。它不必把所有逻辑写成代码，但会把领域说明、模板、参考资料和可重复脚本组织成一个包，让模型或执行环境在合适任务中加载。

例如“把会议记录转成行动项”：Prompt 可以描述本次输出；Skill 还要定义输入最小条件、字段合同、缺失值规则、冲突处理、检查脚本和评测案例；如果最后还要自动写入任务系统，则要另接受控工具或工作流。不要把这三层混成一个词。

开放 Agent Skills 规范中，一个 Skill 以目录为单元，入口是 `SKILL.md`，可以包含脚本、参考资料和资产。渐进式披露的意义是：系统先根据名称与描述判断是否相关，触发后才读取说明，需要时再加载资源。这既节约上下文，也要求描述足够精确，不能写成“处理所有办公任务”。

## 6:00–11:00｜五部件：触发、资源、步骤、停止、评测

第一是触发。回答“什么请求应该用、什么请求不应该用”。会议行动项 Skill 适用于从已提供的会议记录提取行动项；不适用于替用户决定优先级、根据记忆补负责人、自动发送通知。

第二是资源。包括输入材料、术语、输出合同、参考样例和可调用工具。资源必须说明来源与版本；能读取并不等于获准使用。

第三是步骤。只写真正改变结果的顺序。例如先提取原文事实，再识别行动表达，再填负责人和截止日期，再检查冲突，最后输出。可由脚本稳定完成的格式、日期或必填检查，不要全部依赖模型自由生成。

第四是停止。输入为空、负责人缺失、日期冲突、要求执行未授权动作时怎么办？成熟 Skill 会明确：保持未知、列出问题、在模型前停止，或转人工。停止规则把安全从提醒变成行为。

第五是评测。至少需要一组正常案例和边界案例、有/无 Skill 或旧/新版对照、评分规则、版本与 Trace。没有评测，我们只有“作者觉得这份说明不错”。

把五部件连起来，就是今天的核心判断：Skill 不是一段更长的话，而是一套能被发现、执行、停止和比较的工作方法。

## 11:00–16:00｜仓库演示：一个课堂候选怎样留下证据

现在看仓库中的 `examples/meeting-to-action-skill/`。入口 `SKILL.md` 说明触发、输入和流程；`references/output-contract.md` 定义输出字段；`examples/` 有四组输入和人工参考答案；`scripts/` 有机械检查和评测；`evals/runs/` 保存了本地模型输出与 Trace。

四个案例分别测试：正常输入、负责人或日期缺失、事实冲突、请求执行未授权动作。最后一个案例要求“把结果直接发出”，Skill 必须在调用模型前停止，因为它没有发送授权。

保存的课堂快照使用同一本地模型和四个虚构案例：模糊基线通过 1/4，加载 Skill 后通过 4/4。这个数字可以证明什么？它证明在这四个已知案例、这个版本和这次保存运行中，Skill 输出满足当前评分合同。

它不能证明什么？不能证明真实联想会议都能处理，不能证明上线准确率，不能证明其他模型同样表现，也不能证明获得系统权限。样本只有四个，而且部分检查是确定性的。课堂用它展示评测方法，而不是营销准确率。

Trace 里保存输入文件、输出哈希、Skill 哈希、合同哈希、模式和是否在模型前停止。这样后来修改 `SKILL.md` 后，旧结果不会被偷偷当成新版本证据。可追踪性不是堆日志，而是能回答“哪一版、用什么输入、做了什么、为什么停、输出是否被改过”。

## 16:00–20:30｜怎样从真实任务提炼 Skill

第一步，选择稳定、重复、可验收的任务。高频不等于适合；如果每次目标完全不同、责任高度依赖专家判断，先做 Prompt 模板或辅助分析。

第二步，收集少量真实感但合规的成功与失败样例。先写人工认可的参考输出，尤其保留缺失、冲突和未授权请求。

第三步，提炼五部件。把通用规则放在 `SKILL.md`，大量领域资料放到 references，可机械检查的部分放脚本，不要把所有内容复制到一个巨大文件。

第四步，做基线和候选对照。冻结测试案例，先看没有 Skill 时如何，再加载候选。评分既可以有确定性断言，也要有人检查内容是否真正有用。

第五步，版本化并记录限制。通过小样本只是候选；要进入受控试点，还需更有代表性的任务、权限、监控和责任人。

## 20:30–24:30｜练习：五分钟 Skill 设计卡

请选一个模拟任务：“把每周跨部门会议记录整理成行动项草稿”。四分钟内填写五栏：触发、资源、步骤、停止、评测。至少写一个不触发场景和两个停止条件。

（两分钟个人写；一分钟同桌检查是否把输出格式误写成完整 Skill；最后一分钟请一位同事说出评测案例。）

讲评时注意：如果只写“使用专业语言、认真分析、输出表格”，这仍然只是 Prompt。加入输入要求、参考合同、检查脚本、冲突规则、未授权停止和测试案例，才开始形成 Skill。

一个好的不触发例子是“用户要求自动给客户发邮件”；一个好的停止条件是“负责人缺失时填待确认，不根据职位猜测”；一个好的评测案例是“同一句会议记录里出现两个不同截止日期，输出必须并列冲突并请求确认”。

## 24:30–27:00｜收束：复用能力来自合同与证据

请记住成熟度阶梯：长 Prompt、有说明的文件包、可运行候选、代表性评测通过、受控试点、获批生产。团队沟通时说清自己在哪一级，比笼统说“我们已经有 Skill”更专业。

下一课会把 Skill 放进更大的执行环境：什么时候只调用一个只读工具，什么时候用固定工作流，什么时候才需要 Agent，以及哪些动作必须人工确认。

今天带回岗位的动作：把你收藏夹里最好用的一条 Prompt 拿出来，用五部件审计。如果缺停止和评测，先补这两项；它们通常最能暴露真实风险。

快速收束句：Prompt 让一次委托更清楚；Skill 让一种工作方法可发现、可执行、可停止、可比较。
