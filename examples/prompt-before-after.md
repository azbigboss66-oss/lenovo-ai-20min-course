# Prompt 前后对照：把会议记录变成周报与行动项

> 教学模拟：以下项目、人员、日期和客户代号均为虚构，只用于课程练习，不代表联想真实项目或内部流程。

## 模拟原始记录

```text
项目代号：Horizon
会议日期：9 月 8 日

- 试点演示材料需要在本周四前完成，李敏负责汇总。
- 王宁今天更新样机清单；记录中没有写最终提交时间。
- 客户名称继续使用“客户 A”，不要在外发材料中写真实名称。
- 培训拟安排在下周，具体日期尚未确认。
- 当前风险：两个关键测试结果仍在等待，可能影响演示材料定稿。
- 下一次同步会暂定周五上午，会议邀请尚未发出。
```

## 版本 0：只有愿望

```text
把下面会议内容整理一下。
```

### 为什么不够

- “整理”可能意味着摘要、邮件、周报、行动项或 PPT。
- 没有目标读者，模型无法判断应该保留多少背景。
- 没有事实边界，模型可能为了完整而补日期或客户信息。
- 没有输出合同，结果难以进入后续协作。
- 没有验收方式，使用者只能凭感觉判断“写得好不好”。

### 可能出现的失败输出

```text
Horizon 项目进展顺利，团队将在下周一开展培训。
王宁负责在周三前完成样机清单，周五上午召开下一次会议。
```

这段话读起来流畅，却包含两个原文没有提供的事实：“下周一”和“周三前”。“进展顺利”也忽略了两个关键测试仍在等待的风险。

## 版本 1：五字段任务合同

```text
# 任务目标
请根据下方会议记录，为 Horizon 项目负责人生成一页中文周报，
使其能够判断本周进展、主要风险和下一步。

# 必要上下文
仅使用 <meeting_notes> 中的材料。项目代号和“客户 A”均为教学模拟标识。

<meeting_notes>
[粘贴模拟原始记录]
</meeting_notes>

# 约束条件
- 不调用外部知识，不补充原文没有的日期、负责人、状态或客户身份。
- 把推测、冲突和缺失信息放入“待确认事项”，不得写成事实。
- 保留“客户 A”代号。
- 全文不超过 600 个中文字符。

# 输出形式
严格按以下顺序输出：
1. 本周结论：最多 3 条，每条先写结论，再写依据。
2. 风险与影响：风险、可能影响、当前证据。
3. 行动项表：事项 | 负责人 | 截止日期 | 原文依据 | 状态。
4. 待确认事项：只列影响执行的信息缺口。

# 验收与停止条件
- 每个事实必须能在原始记录中定位。
- 负责人、日期或状态缺失时填写“未提供”，禁止猜测。
- 原始记录为空时停止生成，回复“请提供会议记录”。
- 提交前检查行动项表是否正好包含 5 列。
```

## 五字段分别解决什么

| 字段 | 本例内容 | 预防的失败 |
|---|---|---|
| 目标 | 给项目负责人一页周报，用于判断进展、风险和下一步 | 输出虽然完整却不适合读者 |
| 上下文 | 仅使用指定会议记录 | 混入模型记忆或无关背景 |
| 约束 | 不补事实、保留代号、限制篇幅 | 泄露、虚构和信息过载 |
| 输出 | 四段结构和五列表格 | 格式漂移、难以复用 |
| 验收与停止 | 可定位依据、缺失写“未提供”、空输入停止 | 无证据也继续生成 |

## 初版输出示例：结构合格但仍需业务复核

下面的结果满足结构合同，但仍故意保留一个可讨论的问题：“进行中”并未在原始材料中明确出现。课堂上可用它说明，结构检查通过不等于事实检查通过；更严格的版本应将这两项状态写为“未提供”。

- 周五同步会的最终时间与邀请负责人。

## 讲师点评

这个结果仍需人复核。例如“进行中”是根据动作语气形成的状态判断，如果业务上要求完全不推断，Prompt 应进一步规定状态只能使用原文明确值，否则一律写“未提供”。这说明 Prompt 不是写完一次就永远正确，而要通过真实样例暴露隐含规则，再迭代合同。

## 什么时候增加 Few-shot

若团队对“本周结论”的写法有稳定格式，可以在 Prompt 中加入一到两个经过脱敏、人工确认的输入输出示例。示例应覆盖不同情况，而不是重复同一种顺利场景。Few-shot 只在当前上下文中展示模式，不会永久改变模型参数。

## 自检问题

1. Prompt 是否明确给谁使用、用于什么决定？
2. 模型可使用的事实来源是否封闭？
3. 有哪些高代价错误被写进约束？
4. 输出能否直接被下一位同事或系统接收？
5. 信息不足时，模型是否知道标记、询问或停止？
